# Uno / .NET Scaffolding & XAML Rules

Load this file when the task touches Uno Platform scaffolding, project setup, MVUX/MVVM choice, XAML binding style, or preview SkiaSharp pinning.

## SDK Versions

- Always use the **latest stable .NET SDK and Uno.Sdk version**.
- Check Uno Platform docs or NuGet before scaffolding. Never default to an older TFM out of habit.
- Validate the environment with `uno-check` when scaffolding fails or first-run is unstable.

## New App Scaffolding

- Use `dotnet new unoapp -preset recommended`.
- Single Project layout is the default.
- Skia renderer is the default since Uno.Sdk 6.0.
- `UnoFeatures` in csproj controls which Uno packages are included.
- After `dotnet new unoapp`, copy the canonical Claude Code MCP config from `~/.claude/templates/uno/.mcp.json` into the new project root (alongside the `.sln`) before the first build. This seeds the `unoannotation`, `uno`, and `uno-app` MCP servers for every app. The user's `New-UnoApp` PowerShell function does this automatically when they scaffold from the terminal — mirror it when scaffolding on their behalf.
- Run `dotnet build` after scaffolding to confirm it compiles before doing anything else.

## MVUX vs MVVM

Default to **MVUX** for app-level state with async/reactive data flows:
- Feeds from services
- Cached lists
- Paginated data
- Network-bound state

Use **MVVM** (`CommunityToolkit.Mvvm`) only for:
- Samples or demos
- Single-page tools
- Pages whose state is mostly imperative toggles plus a few observable properties

State the choice explicitly when scaffolding and explain why. Do not switch mid-project.

MVUX shape:
- Models are `partial record` (immutable).
- Source generator produces the bindable ViewModel from the Model.
- `IFeed<T>` for read-only async data, `IState<T>` for mutable, `IListState<T>` for selection-bindable lists.
- `FeedView` handles loading / error / empty / data states.
- Public methods on Models auto-generate commands.
- Data entities are immutable records; use `with` for updates.

## XAML Binding

- **MVUX pages → `{Binding}`.** MVUX sets `DataContext` to a source-generated bindable proxy that projects `IFeed`/`IState` into bindable values through the classic `{Binding}` pipeline. `x:Bind` compiles against `x:DataType` and binds the declared member as-typed, so it bypasses that projection — and `FeedView` reshapes the DataContext to a `Data` wrapper with no static `x:DataType` to compile against. `x:Bind` therefore does **not** work for the MVUX data surface. Two-way to state is `{Binding State, Mode=TwoWay}` (not `.Value`); FeedView content is `{Binding Data.X}`.
- **Non-MVUX / MVVM / static XAML → prefer `x:Bind`** (compiled, type-checked, faster). This default holds **only** when the `DataContext` is a plain typed object, not an MVUX proxy.

## Navigation (Region-Based)

- Use XAML attached properties: `Navigation.Request`, `Region.Attached`, `Region.Name`.
- Do not navigate from code-behind.
- Register routes centrally via `ViewMap` / `DataViewMap` / `ResultDataViewMap`.

## Styling Rules

- Never hardcode hex colors. Use Material color/brush resources.
- Never set explicit font sizes. Use Material type-scale styles.
- Use Lightweight Styling resource keys for control-level overrides.
- New styles go in `App.xaml` or under `Themes/`.
- Material theme is the default recommendation.

## Platform Strategy

- Early: POC on all targeted platforms.
- Middle: Develop primarily on Windows (best tooling).
- End: Test equally across all platforms.
- Platform-specific code via file suffixes (`.Android.cs`, `.iOS.cs`) or runtime checks.

## Extensions Stack

- Hosting: `IHostBuilder` pattern.
- DI: Microsoft.Extensions.DependencyInjection.
- Configuration: Options pattern (`IOptions<T>` / `IWritableOptions<T>`).
- HTTP: Kiota preferred for OpenAPI clients; Refit acceptable.
- Logging: `Microsoft.Extensions.Logging` (Serilog optional).
- Auth: MSAL / OIDC / Web / Custom — pick by scenario.
- Localization: `.resw` files with runtime culture switching.

## SkiaSharp 4 Capability Note

GA = `4.148.0` (2026-06-29). Verified against the `v4.148.0` managed binding source on 2026-06-30. Uno Platform is now a co-maintainer of SkiaSharp. For implementation patterns, load the `skiasharp-uno` skill; see also [[reference-skiasharp-uno]].

- Do not describe SkiaSharp 4 as "2D-only" or "a 2.6D canvas drawer." It is a 2D canvas API with GPU acceleration (GL, Direct3D, Metal, Vulkan), runtime SkSL shaders, an image-filter graph, and a mesh primitive.
- **CORRECTION (was wrong): there is NO `SKMesh` type in the GA managed binding.** Verified by grep of `binding/` and `source/` at tag `v4.148.0`: no `SKMesh`, no `SKCanvas.DrawMesh`, and zero `mesh` bindings in `SkiaApi.generated.cs`. Do not claim `SKMesh` exists in 4.148.0.
- **The mesh primitive that DOES exist is `SKVertices`** (`SKVertices.CreateCopy(SKVertexMode, positions, texs, colors, indices)`), drawn with `canvas.DrawVertices(...)`. Use it for triangle meshes, gradient meshes, and textured 3D. Projection, lighting, and depth sort happen in user shader/CPU code, then emit triangles through `SKVertices`, or drive a full SkSL shader via `SKRuntimeShaderBuilder`.
- The upstream Skia `SkMesh` (custom-mesh-with-SkSL-vertex+fragment) API is not bound in 4.148.0. If a future preview binds it, re-verify before relying on it.
- Wiesław Šoltés's "Mesh Modeler" Uno + SkiaSharp sample almost certainly uses `SKVertices`/`DrawVertices` or a custom P/Invoke, not a GA `SKMesh` binding. Confirm the build before citing it as `SKMesh` proof.
- Preferred phrasing: "SkiaSharp is a 2D canvas API; in v4 you build meshes and 3D with `SKVertices`/`DrawVertices` plus runtime SkSL shaders, on a GPU-accelerated backend."
- Graphite (newer GPU backend) is preview only (`4.150.0-preview.2.1`), not GA.
- v4 GA capabilities to lean on instead: variable fonts (`SKFontArguments.VariationDesignPosition`), color font palettes (`PaletteIndex`/`PaletteOverrides`/`SKTypeface.Clone(paletteIndex)`), animated WebP (`SKWebpEncoder.EncodeAnimated`), runtime shaders, and the image-filter graph (`CreateShader`/`CreateDisplacementMapEffect`/`CreateArithmetic`/`CreateBlur`).

## Preview SkiaSharp + Uno

When pinning a preview SkiaSharp (e.g. 4.x while Uno stable still bundles 3.x):

- The matching **Uno.Sdk dev version** is usually required so the bundled managed SkiaSharp matches the native lib.
- Set `<UnoDisableLottieSkiaVersionCheck>true</UnoDisableLottieSkiaVersionCheck>` to suppress Uno's Lottie/Skia version assert.
- Cross-reference the official SkiaSharp Uno gallery sample for the matching Uno.Sdk version: `samples/Gallery/Uno/SkiaSharpSample.Uno.csproj` at the SkiaSharp tag.
- Known good combo (as of TypeLab, 2026-04): `Uno.Sdk 6.6.0-dev.208`, `net10.0-desktop`, SkiaSharp 4.x preview, `UnoDisableLottieSkiaVersionCheck=true`.
- If a SkiaSharp/native version mismatch hits at runtime, verify the Uno.Sdk dev version before patching managed code.

## Runtime Gotchas (validated on Atlas, 2026-06, Uno.Sdk 6.5.36 / Toolkit 8.4.2)

- **`MainWindow.UseStudio()` blocks window display when no DevServer is reachable — on STABLE too** (validated BillCal, 2026-08-26, Uno.Sdk **6.6.42**, `net10.0-desktop`). The process starts and stays alive, but `MainWindowHandle` is `0` and enumerating the process's top-level windows finds **no XAML window at all** (only `GDI+ Hook Window Class`, `IME`, `PseudoConsoleWindow`) — so it is not merely "hidden", it is never created. Console shows `Uno.UI.HotDesign.Client.Logic.DevServer.RemoteControlService: DevServer isn't able to connect` and then nothing. *This refines the older "Debug builds on dev Uno.Sdk keep the window hidden" note below: the cause is `UseStudio()`, not the dev channel, and it reproduces on stable.* Fix: launch via `uno_app_start`, or gate the call — `if (Environment.GetEnvironmentVariable("APP_NO_HOTDESIGN") != "1") MainWindow.UseStudio();` — so headless verification runs can opt out. Note a desktop Uno app is a windowed process: redirected stdout/stderr capture **nothing**, so add a file-based trace if you need startup diagnostics.
- **Synthesized mouse/keyboard input cannot drive an Uno desktop app from a Claude Code session** (validated BillCal, 2026-08-26). Windows refuses `SetForegroundWindow` from a background process, so the app window stays behind and every click lands on whatever is actually on top. **`PrintWindow` is occlusion-proof, so captures keep looking perfect and completely mask the problem** — the symptom reads as "my Click handler is broken". Diagnostic: `WindowFromPoint(target)` and compare the owning PID against the app's; also check `IsIconic` (a minimised window's `GetWindowRect` yields a ~160x28 sliver that captures as a tiny strip). Additional trap: `mouse_event` `MOUSEEVENTF_ABSOLUTE` normalisation against `GetSystemMetrics(SM_CXSCREEN/SM_CYSCREEN)` landed ~15% off on a 1920x1200 display, and a closed-loop rescale diverged. Forcing z-order with `SetWindowPos(HWND_TOPMOST)` + `ShowWindow` on the Skia host HWND **destroyed the window** (`MainWindowHandle` went to 0) — do not do that here, despite it working on DeskBoardUno. Conclusion: use the App MCP for interaction; when it is unavailable, add `#if DEBUG` env-var hooks that pin the start state (scene, open row, cursor month, open panel, a seeded mutation) so captures are deterministic without a pointer.
- **`CompositionEffectBrush` paints nothing on Uno Skia desktop, while reporting `LoadStatus.Success`** (measured BillCal, 2026-08-26, Uno.Sdk 6.6.42, `net10.0-desktop`). This is the real reason Composition blur is unavailable — *not* "the Win2D wrapper is internal", which is only half true. Isolated step by step: `Compositor.CreateSpriteVisual()` + `ElementCompositionPreview.SetElementChildVisual` **renders** (a colour brush filled the window pure `255,0,0`); `CompositionVisualSurface` with `SourceVisual`/`SourceSize` **captures correctly** (a plain `CreateSurfaceBrush(surface)` painted a visible copy of the subtree); but swapping that same surface brush behind a `CompositionEffectBrush` renders **nothing at all**. The effect is genuinely recognised — internal `EffectHelpers.GetEffectType(CLSID_D2D1GaussianBlur)` returns `GaussianBlurEffect`, which is in its supported enum alongside ~30 others. Not a property-mapping bug either: baking the amount in before `CreateEffectFactory` and answering both `BlurAmount`/`StandardDeviation` in `GetNamedPropertyMapping` (returning `Unknown` rather than throwing for unrecognised probes) changed nothing. **What IS public and usable:** `Compositor.CreateVisualSurface/CreateSurfaceBrush/CreateEffectFactory/CreateSpriteVisual`, `CompositionVisualSurface`, `CompositionEffectBrush`, `SpriteVisual`, and `IGraphicsEffect` / `IGraphicsEffectD2D1Interop` / `GraphicsEffectPropertyMapping` (in `Uno.dll`, namespace `Windows.Graphics.Effects[.Interop]`) — only `Microsoft.Graphics.Canvas.Effects.GaussianBlurEffect` is internal, and hand-writing that description is ~40 lines and compiles fine. So the blocker is the render step, not the API surface. Practical consequence: **treat blur as unavailable on Skia desktop and design entrances/transitions to read on opacity + translate + scale alone**; keep the capability probe (`TryAttach` returning null) so it lights up if a later Uno lands effect-brush rendering. Re-verify with a colour-brush sprite first — if that does not paint, the problem is your host element, not the effect.
- **A whitespace-only `TextBlock` measures to zero width on the Uno Skia text stack** (validated BillCal, 2026-08-26, Uno.Sdk 6.6.42) — including U+00A0, and the glyph *is* present in the font's cmap. This bites the per-character workaround for the `CharacterSpacing` no-op (see below): a label laid out one `TextBlock` per glyph loses every space, so `OPTIMIZE SPREAD` renders as `OPTIMIZESPREAD`. Fix: emit an empty `TextBlock` with an explicit `Width` equal to the mono advance, measured once per (face, size) from a probe block containing `"0"`.
- **MVUX bindable generation is recursive over feed value types and fails on modern record shapes** (validated BillCal, 2026-08-26, Uno.Extensions.Reactive 7.2.3). With implicit bindables on — or with `[ReactiveBindable(true)]` on the model — the generator emits proxies for *every* type its feeds carry, then fails to compile them: `CS9035` for records with `required` members, and `CS0019`/`CS0023` (`??` and `?.` on a non-nullable) for `record struct` types. Also `KE0001`: any record with an `Id`/`Key` property must be `partial`. Options: make the domain records `partial` and non-`required`, or — when nothing binds two-way through XAML — set `[assembly: ImplicitBindables(IsEnabled = false)]` and bind `FeedView.Source` to the plain model record as the `DataContext`; `IFeed<T>` resolves through `{Binding}` directly. Note the attribute takes a named argument (`IsEnabled = false`), not a positional bool.
- **`IState<T>` will not accept a nullable value type** — `State.Value(this, () => (int?)null)` silently infers `IState<int>` and fails with `CS0266`. Use a sentinel on the non-nullable type (0 for "no day selected") or wrap it in a record struct.
- **Uno rejects a `ResourceDictionary` inside a `Setter.Value`** (`UXAML0001: MarkupExtension 'ResourceDictionary' is not supported`), so the WinUI idiom of scoping lightweight-styling keys via `<Setter Property="Resources">` does not compile. Put the theme-resource overrides at app level instead.

- **Creating a secondary `Window` disturbs the main window's FullScreen presenter on `net10.0-desktop`** (validated DeskBoardUno, 2026-07-31, Uno.Sdk 6.6.42): applying `OverlappedPresenter.SetBorderAndTitleBar`/`AppWindow.Resize` to a secondary window *before* its first activation can hit the main window instead (main reverts to overlapped-maximized, rect −8,−8); even a clean secondary-window close can knock the main FullScreen presenter out. Fix: defer the secondary window's presenter/size/position work to its first `Activated` with a non-deactivated state, and after the secondary window closes re-assert the main overlay (~300 ms delay, then cycle `SetPresenter(Default)` → `SetPresenter(FullScreen)` — a plain re-`SetPresenter(FullScreen)` can no-op because AppWindow thinks it's already fullscreen). Also: subscribe deactivate-to-close handlers only after first activation, or the popup closes itself during the activation race.
- **Synthesized input for Uno Skia desktop testing: `SetCursorPos` moves are invisible to the app** (validated DeskBoardUno, 2026-07-31): press/release inject fine via `mouse_event`, but pointer-move events only arrive when movement is injected through the input stream — use `mouse_event(MOUSEEVENTF_MOVE|MOUSEEVENTF_ABSOLUTE, x*65535/w, y*65535/h, …)`. A drag scripted with `SetCursorPos` steps looks like a press with zero movement (selection works, drag/ink silently don't).
- **`AppWindow.MoveAndResize` is a silent no-op on `net10.0-desktop`** (validated DeskBoardUno, 2026-07-31, Uno.Sdk 6.6.42): the call returns without effect and the window keeps its default rect — the Uno0001 analyzer warning is truthful. The DeskBoardUnoPoc "MoveAndResize ok" log line was a false positive (no exception ≠ resized). For fullscreen overlays use `AppWindow.SetPresenter(AppWindowPresenterKind.FullScreen)`; for sized windows use `AppWindow.Resize` (documented as implemented). Ex-style stripping, `WS_EX_TOOLWINDOW`, topmost via `SetWindowPos`, and `ShowWindow(SW_HIDE/SW_SHOW)` cycles all work on the host HWND, and the Skia swapchain survives repeated hide/show (three cycles verified by composited screenshots).
- **DrawerControl cannot be a docked always-open panel.** While open, its light-dismiss overlay stays visible and hit-test-visible over the main content; `IsLightDismissEnabled=false` only makes it swallow taps silently. Symptom: nothing in the content area is clickable. Dock panels as Grid columns on wide form factors; use DrawerControl only for transient/narrow layouts.
- **DrawerControl property setters crash at XAML parse.** `DrawerDepth`/`OpenDirection`/`FitToDrawerContent` changed-callbacks dereference template parts before `OnApplyTemplate` and abort page navigation with `_drawerContentControl is null` (FrameNavigator logs "Unable to navigate to page"). Set them in `Loaded` if you must use the control.
- **MVUX generator reserves `Model`** on the generated ViewModel — a feed/state named `Model` on the model record collides (CS0102). Pick another name (e.g. `Graph`).
- **`IState<T>` of a nullable reference type fights the `notnull` constraints.** Use `IState<T>` non-nullable + `State<T>.Empty(this)`; absence is None, FeedView's `NoneTemplate` renders it. Clear with `UpdateAsync(_ => null)`.
- **Custom DPs in DataTemplates don't receive `ThemeResource`, and theme-dictionary custom keys can fail even with `StaticResource`.** Put app-specific semantic Colors/Brushes in a plain root-level dictionary merged in App.xaml (single-theme apps lose nothing); keep only Material role overrides in `ColorPaletteOverride.xaml`.
- **Inside FeedView templates, reach the page VM via `{Binding Parent.X}`** (FeedViewState exposes Parent). ElementName-to-page bindings work inside ItemsRepeater item templates (`{Binding DataContext.X, ElementName=Root}`), so per-item DPs can observe page state.
- **App MCP (uno-app devserver) flow:** the MCP server is `dotnet dnx uno.devserver --mcp-app` started in the project dir; `--mcp-wait-tools-list` holds the `tools/list` reply until the **devserver upstream** connects (~3.7 s on a warm `dnx` cache, no app launch needed), then returns the full set at once. It must start when a `.sln` exists (reconnect via `/mcp` after scaffolding); launch the app with `uno_app_start`, not bare `dotnet run`.
- **Project `.mcp.json` is loaded from the session root, not the shell's working directory** (validated AotLaunchLab, 2026-08-04). A session started in a parent folder never registers the project's `uno-app` server at all. `cd` into the project does not retroactively load it, and `/mcp` only reconnects already-registered servers — it will happily report "Reconnected to uno" (the global HTTP docs server) while `uno-app` stays absent, which reads as a successful reconnect. Check for `uno_health` / `uno_execute_tool`: if the only Uno tools are `uno_platform_docs_search` / `_fetch`, the app MCP was never loaded and no reconnect will fix it. Start a fresh session rooted in the project folder.
- **Whether the app tools are listed directly depends on `--mcp-wait-tools-list`** (re-validated 2026-08-12, DevServer 6.6.184, raw MCP stdio client; supersedes the RefractionPixels 6.6.166 note that said the tools are always proxied). Measured on 6.6.184:
  - **With** the flag: `tools/list` is held ~3.7 s and returns **all 16 tools directly** — the 14 real `uno_app_*` / `uno_health` / `uno_devserver_diagnostics` tools *plus* the `uno_discover_tools` / `uno_execute_tool` bridge pair. Call the real tools by name.
  - **Without** the flag: `tools/list` replies in ~200 ms with **only the four bridge tools** — `uno_health`, `uno_app_select_solution`, `uno_discover_tools`, `uno_execute_tool`. The rest arrive later via a `notifications/tools/list_changed`, so a client that ignores that notification is stuck at four. Invoke the real ones as `uno_execute_tool {toolName: "uno_app_start", arguments: {...}}`; names and schemas are unchanged, only the call path moved.
  - Diagnostic: seeing only four tools means the flag is missing (or the client dropped the notification), not that the App MCP is broken. `uno_discover_tools` confirms the upstream set either way.
- **`uno-app` emits `tools/list_changed` without declaring `tools.listChanged`** (validated 2026-08-12, DevServer 6.6.184). Its `initialize` capabilities are `{"logging":{},"resources":{},"tools":{}}` — no `listChanged: true` — yet it sends the notification once upstream connects. A spec-strict MCP client may legitimately ignore it. **Keep `--mcp-wait-tools-list` in every `.mcp.json`**, including for third-party clients (GitLab Duo, Cursor, Copilot): with the flag, `listChanged` support stops mattering because the first `tools/list` reply is already complete.
- **`SdkNotInCache` on first contact is recoverable without `/mcp`.** `uno_health` can report `Unhealthy` / `toolCount: 0` / Fatal `SdkNotInCache` even when `dotnet build` just succeeded. `uno_app_select_solution` with `forceRestart: true` on the explicit `.sln` path restarts the DevServer and brings it to `Healthy` / `upstreamConnected: true`; that is more direct than a `/mcp` reconnect. `uno_app_pointer_click` coordinates can miss — prefer `uno_app_element_peer_default_action` with refs from `uno_app_visualtree_snapshot`; checkbox peers may not expose a default action, and Button peer invokes are flaky (retry on "Failed"). Visual-tree bounds are layout slots and ignore ZoomContentControl pan/zoom transforms. The MCP cannot inject drags — verify drag/pan features with a human or by asserting the post-state (e.g. write a layout file and confirm Load applies it).
- **App MCP tools require a signed-in Uno Platform account** (validated CapacityPlanner, 2026-07-28, DevServer 6.6.176 / Uno.UI.App.Mcp 1.1.4). With the user signed out, `uno_health` reports Healthy / `upstreamConnected: true` but `toolCount` stays 0, `uno_discover_tools` returns empty, and every `uno_execute_tool` fails with an opaque "Request failed (remote)" — even with a devserver-connected app running. After sign-in via Uno Settings + app relaunch, all 11 tools register immediately. Check sign-in state before diagnosing a DevServer regression. Also from the same pass: `uno_app_pointer_click` takes **client-area coordinates** (the same pixel space as `uno_app_get_screenshot`), not screen coordinates — screen coords return "Success" but hit nothing; and ToggleButton peers fail both `peer_default_action` and an explicit `Toggle` action (same family as the checkbox-peer gap), so drive ToggleButtons with client-coordinate clicks.
- **A held `CompositionTarget.Rendering` subscription forces the Uno Skia desktop compositor to produce frames at display refresh FOREVER, at ~50-70% of one core** (probe-validated TransitionsGallery, 2026-08-17, Uno.Sdk 6.6.42, `net10.0-desktop`; cost is mostly per-frame composition/present — likely a vsync busy-wait in the swap — and is identical in Release). Per-frame cost measured ~11-15ms of CPU per frame *regardless of content*; an app that "idles" with a Rendering hook attached is a 60fps app. Consequences: (a) use Rendering only for one-shot animations that unsubscribe on completion; (b) drive continuous decorative loops (shimmers, pulses) from a shared ~30fps `DispatcherTimer` that calls `Invalidate()` — a timer does not force frames, each invalidation produces exactly one, and co-subscribed loops coalesce into the same frame; (c) a `RepeatBehavior="Forever"` storyboard has the same permanent-pump cost and cannot be throttled — port slow decorative storyboard loops to the timer. **A Forever storyboard keeps costing while its target is hidden; `Stop()` does reclaim it** (isolated repro `ComponentStatesLab/PulseCpuRepro`, 2026-08-18, Uno.Sdk 6.8.0-dev.12, `net10.0-desktop`, **Release**, 3 samples/mode after a 15s settle): app idle **0.1%** of one core, Forever opacity keyframe animation on one 220×24 `Border` running **29.4%**, same storyboard running with the target `Visibility="Collapsed"` **17.3%**, after `Stop()` **0.3%**. Two consequences: (a) one trivial decorative animation costs ~a third of a core, so budget them; (b) **collapsing a skeleton layer does not stop its animation** — always `Stop()` on state exit, or use a `DispatcherTimer` writing `Opacity` (0-2%) which cannot be orphaned. *Supersedes an earlier note here claiming `Stop()` does not reclaim the pump — that measurement was confounded by concurrent app instances.* Also probe-confirmed: invalidation is per-element (a dirty `SKCanvasElement` does NOT re-execute other elements' `RenderOverride`), so caching settled Skia content into `SKPicture` buys nothing on this target.
- **`EffectiveViewportChanged` reports the WINDOW viewport for every element on Uno Skia desktop — it cannot detect off-screen** (probe-validated TransitionsGallery, 2026-08-17, Uno.Sdk 6.6.42): elements far outside a ScrollViewer receive `visible=<full window size>` at load and on every scroll, so viewport-gating built on it silently never gates (loops "paused off-screen" actually ran forever — see the Rendering-pump gotcha above for what that costs). Workaround: walk to the ancestor `ScrollViewer`, hook `ViewChanged` + `SizeChanged`, and intersect `element.TransformToVisual(scrollViewer)` bounds with `ViewportWidth/Height` (~200px pre-roll margin). Working implementation: `TransitionsGallery/Motion/ViewportGate.cs` (+ `LoopClock.cs`/`FrameLoop.cs` for the timer-driven loop pattern).
- **`uno_app_start` can fail persistently with "No process is associated with this object" right after an Uno.Sdk bump** (validated TransitionsGallery, 2026-08-17, DevServer 6.6.184, 6.5.36→6.6.42 via global.json). Two `uno_app_select_solution forceRestart:true` cycles did not clear it, while the built exe ran fine when launched directly — and a **directly-launched Debug build self-connects to the DevServer via RemoteControl**, after which every App MCP tool works against it (`uno_app_get_runtime_info` confirms the PID). So the fallback is `Start-Process` the exe yourself, not more launcher retries. Related: on stable 6.6.42 the window SHOWS when launched without `uno_app_start` (the hidden-window gotcha below is specific to dev-channel Uno.Sdk builds), and App MCP add-in 1.2.44 rejects screenshot paths outside the workspace ("Security error: path must be within the current working directory") — save captures under the project and clean them up.
- **After a C# hot reload, driving a demo through a still-valid automation ref can act on an orphaned pre-HR instance** (validated TransitionsGallery, 2026-08-17, Uno.Sdk 6.5.36 / DevServer 6.6.184). HR that touches a hosted element's type recreates the visual instance (its tree ref changes) while a `ContentProperty`-style DP on the host can keep pointing at the old object — a Button peer invoke then returns "Success", the click handler runs, and the method executes on the detached instance, so nothing visible happens and there is no error anywhere. Every same-ref invoke *before* the HR works; every one *after* silently no-ops, which mimics the "flaky Button peer" gotcha but retrying never helps. Diagnose by hot-reloading an unmissable render change (e.g. a colour) to prove HR itself applies; recover by restarting the app before further MCP-driven interaction. Screenshot RPC latency through the bridge is ~2 s, so animations shorter than that always capture settled — to photograph a mid-flight state, hot-reload the duration to something long (60 s) on a *freshly restarted* process.
- **SKCanvasElement does not survive a Hot Design round-trip** (validated CapacityPlanner, 2026-07-28, Uno.Sdk 6.5.36 / DevServer 6.6.176). Inside Hot Design's design surface (both Design and Interactive tabs) the element renders blank while regular XAML renders fine; after exiting Hot Design the element **stays blank in the live app** — `Invalidate()` from state changes and a window resize both fail to revive it. App logic keeps running; only the drawn surface is dead. Recovery: restart the app. Don't enter Hot Design in an app whose primary surface is an SKCanvasElement without expecting a restart afterward; candidate app-side workaround (unverified): recreate the element and reassign it as the host child on `Loaded` after the designer exits.
- **`{Binding Refresh}` inside `FeedView.ErrorTemplate` is a silently dead button** (validated ComponentStatesLab, 2026-08-17, Uno.Sdk 6.8.0-dev.12). The ErrorTemplate's DataContext is the **thrown `Exception`**, not `FeedViewState` — confirmed by `uno_app_get_element_datacontext`, which serialised the Retry button's DataContext as `System.InvalidOperationException` with the service's own message and zero `Refresh`/`FeedViewState` members. `Command` binds to null, the button still renders enabled and still reports `[i]` invoke, and clicking it does nothing. `{Binding Parent.X}` fails there for the same reason (Parent lives on FeedViewState). Fix: `x:Name` the FeedView and use `Command="{Binding Refresh, ElementName=TheFeed}"`, which resolves even from inside a nested `CardContentControl.ContentTemplate`. This one is dangerous because it is invisible to review, to the build, and to screenshots — the error state *looks* perfect. Verify Retry by driving the app to Error, flipping the data source healthy at runtime, invoking the button, and asserting the service ran again.
- **MVUX command parameters from inside FeedView templates don't bind reliably.** A `Command="{Binding Parent.X}" CommandParameter="{Binding Data}"` on a button inside a FeedView ValueTemplate silently no-ops the command. Drive the command from a state the model already holds (e.g. read `await Selected` inside the method) instead of passing the bound item as a parameter.
- **`Feed.AsyncEnumerable(source)`** is the MVUX way to project an `IAsyncEnumerable<T>` push stream (e.g. a service that yields the current value then live updates) into an `IFeed<T>`. `await thatFeed` inside a command returns the latest pushed value, same as `Feed.Async`.
- **`AppModelJson.Options` has `WriteIndented=true`** — never serialize NDJSON wire messages with an indented options object; each message spans multiple lines and breaks line-delimited parsing. Keep a separate compact options instance for the wire.
- **NuGet packaging across ProjectReferences:** a packable project (`PackageId`/`Version` set) that ProjectReferences another emits a package *dependency* on it, so the referenced project must also be packable with a matching version or consumers get an unresolved dependency. Verify with `unzip -p pkg.nupkg '*.nuspec' | grep dependency`.
- **FileOpenPicker** works on Skia desktop and must be called on the UI thread; MVUX commands may run off it, so marshal via the window `DispatcherQueue` (`TryEnqueue`) and bridge back with a `TaskCompletionSource`. On WinUI/WinAppSDK only, the picker also needs `InitializeWithWindow`.
- **Liquid Glass / backdrop effects on Skia targets (validated LiquidGlassLab, 2026-06, Uno.Sdk 6.5.36 / SkiaSharp 3.119.2):** `SKCanvasElement.RenderOverride` draws on the same canvas the window renders to, so `canvas.SaveLayer(in SKCanvasSaveLayerRec { Backdrop = filter })` genuinely samples live app content behind the element. SkiaSharp 3.119 has **no** `SkImageFilters::RuntimeShader` binding — route SkSL through `SKImageFilter.CreateShader(builder.Build())` as the *displacement input* of `CreateDisplacementMapEffect` for refraction. Chromatic aberration = 3 displacement filters at split scales + channel-isolating color matrices + `CreateArithmetic` recombine.
- **`SKRuntimeShaderBuilder` must be created once and cached.** Disposing it (per-frame `using`) frees native state shared with its `SKRuntimeEffect`; the next render AVs with `0xC0000005` in `sk_runtimeeffect_get_uniform_byte_size`. Symptom: first frame fine, crash on next invalidation (e.g. drag). Also: never build Skia filter DAGs per frame in `RenderOverride` (render thread) — cache against built-with values and snapshot DPs to plain fields on the UI thread.
- **ShadowContainer `Shadows` must be set inline per instance.** A shared `ShadowCollection` supplied through a Style setter silently drops the inner-shadow rendering (validated PoolLens, 2026-07, Toolkit 8.4.2) — the build succeeds and outer chrome renders, but `IsInner` shadows vanish. Duplicate the `ShadowCollection` element on each container instead of extracting a style.
- **ShadowContainer with a `LinearGradientBrush` Background hangs the first frame** — the window is created but never shown (validated LagoonSpecimen, 2026-07, Toolkit 8.4.2 + SkiaSharp 4.148 + Uno.Sdk 6.7.0-dev.105). Use a solid brush on the container (the gradient midpoint reads the same) and put any gradient elsewhere.
- **`UIElement.Opacity` does not affect `SKCanvasElement` drawing** — the canvas draws straight onto the window canvas, bypassing the XAML opacity. Bake the alpha into the Skia paint/colors (validated LagoonSpecimen, 2026-07).
- **Variable-font TTFs render their default named instance; `FontWeight` does not select the wght axis** on the Skia text stack — Fraunces variable rendered near-Black everywhere. Ship static instances per weight and expose one `FontFamily` resource per file (validated LagoonSpecimen, 2026-07). **The css2 User-Agent matters** (validated 3× independently, DesignSkillEval runs 10–12, 2026-08-03): an IE6 UA serves **EOT** (Skia silently ignores it → default-sans fallback), old Firefox serves WOFF/WOFF2; the **Android 2.2 stock-browser UA** serves true static TTFs — verify magic bytes `00 01 00 00`. The slices carry **weight-suffixed internal family names** ("Oswald Medium", "Bricolage Grotesque 14pt SemiBold") which the `#fragment` must match exactly, and are latin-subset only (no →, Δ, ≈ glyphs — they render tofu).
- **An implicit `Style TargetType="ContentDialog"` never reaches a ContentDialog *subclass*** (validated IdeaBoard, 2026-08-06, Uno.Sdk 6.6.42). Implicit styles match on exact type, so app dialogs written as `sealed partial class FooDialog : ContentDialog` silently keep stock Material chrome while implicit styles on plain types (TextBox, ComboBox, MenuFlyoutPresenter) apply fine — which makes it look like "dialog styling doesn't work in Uno" rather than a type-match miss. Key the style and assign it at construction. Same trap for any custom-derived control.
- **ContentDialog's panel radius and button chrome are unreachable from a Style** on Skia desktop (same session). `Background` responds to the `ContentDialogBackground` *theme resource key* but not reliably to the style setter; `CornerRadius`, `PrimaryButtonStyle`/`CloseButtonStyle` and the command-row layout are ignored entirely — setting `OverlayCornerRadius` does not round the panel either. Retemplate against the live part names (`Container`, `LayoutRoot`, `BackgroundElement`, `DialogSpace`, `ContentScrollViewer`, `Title`, `Content`, `CommandSpace`, `PrimaryButton`, `SecondaryButton`, `CloseButton`) — get them from a `justMyCode:false` visual-tree snapshot rather than from WinUI generic.xaml, which differs. In a hand-written template the `ButtonsVisibilityStates` group does not hide the button parts even when placed on the template root's first child; bind each button's `Visibility` to its own `*ButtonText` through a string-to-visibility converter instead, which is also self-maintaining.
- **Material sizes ComboBox at 56px**, towering over token fields (~37px) and pill bars (~42px) beside it. Unlike ContentDialog, a plain property-setter implicit style (`Height`, `CornerRadius`, `Padding`, `FontSize`, `MinHeight=0`) does take — no template rewrite needed.
- **`MenuFlyoutItem` DOES invoke via synthesized pointer clicks** on Skia desktop (validated IdeaBoard, 2026-08-06, DevServer 6.6.184) — `uno_app_pointer_click` at the item's client coordinates commits the item and fires its handler. This supersedes the earlier "MenuFlyoutItem invocation resists synthesized input" note. Modifier chords are still unreliable: `uno_app_key_press` with `control` did not open a Ctrl+K palette wired through `PreviewKeyDown` + `InputKeyboardSource`, because the synthesized modifier state is not visible to that query. Verify modifier shortcuts with a human or by asserting post-state.
- **Entering Hot Design kills `uno_app_get_screenshot` for the rest of the process** (same session): after an enter/exit round-trip every capture returns 0 bytes while `uno_app_visualtree_snapshot` and peer actions keep working. Relaunch the app to restore capture. Related to, but distinct from, the SKCanvasElement-goes-blank gotcha below — this app has no SKCanvasElement.
- **Uno Android TextBox + IME: key-level and per-keystroke managed handling are both unreliable** (validated PaperNotes on Pixel 8, 2026-08-04, Uno.Sdk 6.6.42). Soft keyboards never deliver Enter or backspace-at-position-0 as `KeyDown` (they edit via the InputConnection); a zero-width-sentinel + SelectionChanged guard scrambles IME batch commits (text lands reordered/reversed); and even just *reading* `TextBox.Text` inside `TextChanged` during composition races the native↔managed sync and reorders rapid input. For structured text editing on mobile, give the IME one native multiline `AcceptsReturn` TextBox and parse on commit — signal commit with `InputPane.Hiding` (window-resize heuristics don't fire; Uno absorbs the keyboard via visible-bounds padding) plus `LostFocus`.
- **Uno Skia TextBox: the caret is drawn from natural font metrics and ignores LineHeight stamped on the internal text view** (validated PaperNotes, 2026-08-03, Uno.Sdk 6.6.42). Stamping `LineHeight`/`BlockLineHeight` on the TextBlock inside ContentElement moves the glyphs but not the caret (caret sat 17px-tall at the top of a 34px box), and under a stamped line the caret grows 17→34 on the first keystroke. Also: that internal TextBlock is created lazily on the first layout pass after the box becomes visible and starts unmeasured (0×0) — a collapsed-then-shown TextBox renders its text invisible until something re-measures it. For a fixed-leading editor, keep the edit TextBox on natural metrics (caret+glyphs always agree), position it with a Margin drop onto the grid, and let a styled display TextBlock own the ruled layout when not editing.
- **Uno's `Path.Data` mini-language rejects elliptical arcs at runtime** — `A rx,ry` with rx≠ry throws `NotImplementedException` ("arc must be based on a circle") during parse, which is a startup crash if the Path is in initial XAML (validated DesignSkillEval run 11, 2026-08-03, Meridian Release exe died before first frame). Compose curves from circular arcs (`A6,6`) or Béziers instead.
- **`Control.CharacterSpacing` on Button is Uno0001 not-implemented on desktop** — apply letterspacing on TextBlocks inside the content instead (DesignSkillEval run 12, 2026-08-03).
- **Debug builds on dev Uno.Sdk keep the window hidden when launched without a devserver** (bare exe or `dotnet run`; also affects PoolLens). `Get-Process` shows `MainWindowHandle 0`, `IsWindowVisible false`. Launch via `uno_app_start`, or verify with a Release build. For screenshots/recordings of the GL-composited window use `PrintWindow` with `PW_RENDERFULLCONTENT` (occlusion-proof; gdigrab region records whatever covers those desktop pixels, and window-title gdigrab returns black).
- **`IRouteNotifier.RouteChanged.e.Navigator.Route`** gives the current route path (e.g. `patients/123`), not the registered route *name* or the trigger. To resolve it back to a node, match against route templates segment-wise (`{x}` matches anything), then literal-suffix, then view/name. Reverse-of-existing-edge navigations are back-nav — move the live node but don't synthesize a forward edge.
- **A `Grid` with `HorizontalAlignment="Center"` (or any non-Stretch) sizes to content, so star columns holding only an empty placeholder collapse to 0.** Validated LagoonSpecimen v2 (2026-07-15): a bento whose left columns held only an empty measured `Border` (a shared-element dock target) collapsed those `1.14*` columns to zero, so the measured overlay came back 16px wide (one `ColumnSpacing` gap) and the app card rendered as a sliver. Fix: `HorizontalAlignment="Stretch"` + `MaxWidth` so star columns fill regardless of empty cells. A hand-rolled shared-element morph that measures a placeholder rect must ensure that placeholder is actually laid out at full size in the source state.
- **`SKCanvasElement` DOES ride a parent `ScaleTransform` / `Viewbox`** (validated LightWidget, 2026-08-04, Uno.Sdk 6.6.42, `net10.0-desktop`). A `Viewbox Stretch="Uniform"` wrapping a fixed-size Grid that contains both an `SKCanvasElement` and XAML `TextBlock`s scales both together and keeps them pixel-registered — the canvas is not drawn at unscaled window resolution. This closes the open question left by the LagoonSpecimen note below. It makes "design at literal spec coordinates, scale the whole surface uniformly" the correct pattern for fixed-aspect Skia surfaces: put every measured value in the markup/renderer at its real number and let the Viewbox handle sizing. Note the renderer still receives the *unscaled* design size in `RenderOverride`'s `area`, so blur sigmas and stroke widths stay in design units (no manual DPI math).
- **`TextBlock.CharacterSpacing` is a no-op on the Uno Skia text stack** (validated LightWidget, 2026-08-04, Uno.Sdk 6.6.42): 120 units (0.12em) moved the measured ink width by **0px** at 72.5px font size. Same family as the `Control.CharacterSpacing` Uno0001 gap on Button, but silent — no analyzer warning, it just does nothing. For letterspaced display type, lay the string out one character per `TextBlock` in a `StackPanel` with `Spacing` (exact, and leaves glyph shapes alone); a horizontal `ScaleTransform` is the tempting alternative but thickens vertical strokes by the same percentage it widens, which is very visible at w100–200.
- **`AppWindow.Resize` grows the frame before the Skia surface follows** (validated LightWidget, 2026-08-04, `net10.0-desktop`): the app lays out to the new size against the old surface and renders **clipped**, with bare window behind the missing strip. Intermittent — it depends on whether the resize lands before the first render, so it reproduces maybe one run in three. Re-asserting on `Activated` + `SizeChanged` does not reliably fix it (guarding on `AppWindow.Size` short-circuits because the *frame* is already the target size while the surface is not). If a fixed window size is not a hard requirement, don't resize at all and let the layout fit whatever the window is. If a harness needs a known render size, pin the content instead (set explicit `Width`/`Height` on the root `Viewbox`) rather than sizing the window.
- **`PrintWindow(PW_RENDERFULLCONTENT)` can return TRUE and still hand back a blank bitmap** for a Skia GL desktop window (validated Aware, 2026-08-07, Uno.Sdk 6.6.42, `net10.0-desktop`). The capture is silently white while the window is rendering perfectly on screen, and the usual `if (-not $ok) throw` never fires because the call reports success. Symptom: a "blank page" regression that reproduces on *every* build including known-good commits — the tell is that git-bisecting finds no good commit. **A success return is not evidence of pixels: sample the bitmap.** If it is effectively uniform, foreground the window and fall back to `Graphics.CopyFromScreen` (not occlusion-proof, hence a fallback). Working implementation: `Aware/tools/Capture-Window.ps1`.
- **Colour-key your registration when screenshot-diffing an Uno window.** Locating the content rect by luma edge gradient picks up the window frame/title bar and silently compares the wrong crop (cost 3 points of a parity score before it was caught). Have the app paint a keyed backdrop under the content in fixture mode; the content is then the non-key hole inside the key region — two passes, because a `PrintWindow` capture includes non-key chrome around everything.
- **`Add-Type -MemberDefinition` for Win32 P/Invoke under .NET 10 / PowerShell 7:** do **not** pass `-UsingNamespace System.Runtime.InteropServices` (Add-Type already emits that using → CS0105), and keep every `System.Drawing` type *out* of the C# string — `Bitmap`/`Graphics`/`ImageFormat` sit behind type-forwards that `Add-Type` cannot resolve from source (CS0012/CS1069 cascades naming `System.Private.Windows.GdiPlus`). Fully qualify the interop attributes in the string, and do the Bitmap/Graphics/`GetHdc` work in PowerShell itself where `Add-Type -AssemblyName System.Drawing` already works. Working `PrintWindow` capture script: `LightWidget/tools/Capture-Window.ps1`.
- **Shared-element morph on Skia desktop = translate-only is safest.** LagoonSpecimen v2: sizing the showcase card equal to its docked board slot let the explode be a pure `TranslateTransform` on the overlay (no `ScaleTransform`), which sidesteps the open question of whether `SKCanvasElement` water rides a scale. Translate moves the canvas cleanly; keep scale off the app card and put the choreography in the staggered tile entrances instead.
- **An oversized `CornerRadius` (the WinUI "999 pill" idiom) renders as an oval on the Skia renderer** (validated Measures, 2026-08-27, Uno.Sdk 6.6.42, desktop + Android): the radius is reduced per axis instead of clamped to a circle, so an 81x28 button gets 40x14 elliptical corners. Write half the height (`CornerRadius="14"` for 28 epx).
- **A finished `HoldEnd` storyboard keeps overriding the local value; a replay that sets `Opacity = 0` and then animates it up after a `BeginTime` shows the held 1 through the whole delay** (Measures, 2026-08-27). Stop the previous board on the same (target, property) before starting a new one - Measures `Motion/Anim.cs` keeps a `ConditionalWeakTable<DependencyObject, Dictionary<string, Storyboard>>` for exactly this.
- **A `FlipView` sized to its content (`VerticalAlignment="Top"`, no Height) measures each item once; an item that grows later (a chart taking its aspect height on first `SizeChanged`) is clipped, and `ActualHeight` of the item is the clipped slot, so "follow the tallest card" loops** (Measures, Android). Stretch the FlipView to its row and centre the content inside the `FlipViewItem` instead.
- **`Opacity` on a container that covers the screen (a grain/texture layer) becomes a full-screen offscreen surface re-composited every frame; on a Pixel 8 that was a worst frame of 91 ms during a swipe** (Measures, 2026-08-27). Put the opacity on each child (an alpha paint) - worst frame dropped under 34 ms. Measure with `dumpsys SurfaceFlinger --timestats` for the app's SurfaceView layer (Measures `tools/sf-stats.py`), never with an in-app `CompositionTarget.Rendering` monitor, which pumps the frames it measures.
- **Re-parenting a control (e.g. moving cards between a Grid and a FlipView on a breakpoint) fires Unloaded then Loaded; anything Unloaded lets go of (event subscriptions, breath timers, chart references) must be taken back in Loaded** or the control looks fine and silently stops working (Measures: Replay did nothing on the phone).
- **Android `Release` restore can fail with `Microsoft.NETCore.App.Runtime.Mono.win-x64 10.0.1` not found** when the mono toolchain workload manifest is older than the SDK's runtime (10.0.101 manifest vs 10.0.11 runtime on SDK 10.0.303); `dotnet workload update` realigns it. `-p:RunAOTCompilation=false` does not avoid the request.

## WinUI Plugin Selection (for Uno work)

- Keep using: `winui-xaml`, `winui:winui-code-review`.
- Avoid in Uno sessions: `winui:winui-dev`, `winui:winui-packaging`, `winui:winui-dev-workflow` (all Windows/MSIX-only).
- Never use `winui:winui-wpf-migration` — it lands on WinAppSDK desktop only. Use `wpf-to-uno-migration` instead.
- `winui:winui-design` overlaps with `userinterface-wiki-uno` — prefer the Uno one for SafeArea, AutoLayout, platform variance.
- **In Material-themed Uno apps, `winui:winui-design`'s typography and brush tables are invalid.** Its WinUI type-ramp keys (`TitleTextBlockStyle`, `BodyTextBlockStyle`, …) and system brushes (`ApplicationPageBackgroundThemeBrush`, `TextFillColorPrimaryBrush`, …) do not exist under Uno Material — they fail silently (blank text, default backgrounds). `uno-material` wins for typography and color (short keys like `TitleLarge`, brushes like `SurfaceBrush`). Use `winui:winui-design` in Uno sessions only for control selection and layout planning.
- **`PathIcon` clips instead of scaling** (validated Chefs reskin, 2026-08-27, Uno.Sdk 6.6.42, `net10.0-desktop`): a 24-unit Material path at `Width="18"` renders as a fragment (a bell read as a house). Wrap sized PathIcons in a `Viewbox`.
- **`muxc:UniformGridLayout` inside a vertical StackPanel/ScrollViewer stacked one column with huge rows** for `MaximumRowsOrColumns="2"` regardless of `MinItemWidth`/`ItemsStretch` (same session). `FlowLayout` never wrapped either (even 160 px tiles in 342 px) and `GridView`+`ItemsWrapGrid` measured to zero height there. Reliable fix: a small `NonVirtualizingLayout` for `ItemsRepeater` (Chefs reskin `Views/Controls/TwoColumnLayout.cs`), which keeps `uen:Navigation.Request/Data` working.
- **A TabBar driving a Visibility region renders nothing until a nested `RouteMap` is `IsDefault: true`** (same session; uno.chefs registers none for its recipe tabs). Toolkit `TopTabBarStyle` also adds its own selection indicator and equalises item widths — set `SelectionIndicatorContent="{x:Null}"` and a left-aligned horizontal `StackPanel` ItemsPanel for a design underline.
- **Project `.mcp.json` `uno-app` server needs the `.sln` to exist at session start**: scaffolding inside the session leaves the App MCP unregistered for the rest of that session; `/mcp` or a fresh session rooted in the folder fixes it. Headless fallback that worked: `dotnet Chefs.dll` (not the exe) with `APP_NO_HOTDESIGN=1`, a DEBUG `CHEFS_START_ROUTE` hook that resolves seed data through the services, and `PrintWindow` captures (`tools/Capture-Route.ps1`).
